# PersonalAIOS 技术架构

> 文档状态：第三版（对齐四模块产品架构）
> 最后更新：2026-11-20
> 说明：本文档描述技术架构与建议技术路线，**不是技术初始化结论**。标有「建议方案」的内容为推荐而非已确定；标有「待确认」的内容不得直接用于实现。

## 1. 两个维度：业务模块与六层架构

PersonalAIOS 同时存在两个相互独立的维度，避免混淆：

| 维度 | 回答的问题 | 内容 |
| --- | --- | --- |
| 产品功能架构 | 产品要提供什么能力？ | 四个核心业务模块（见 [project-plan.md](./project-plan.md)） |
| 技术分层架构 | 系统内部如何组织？ | 六层逻辑架构（本文第 2 节） |

四个业务模块全部落在六层中的**第三层（业务模块层）**，其余五层为它们提供支撑。

## 2. 六层技术架构

### 2.1 架构示意图

```text
┌──────────────────────────────────────────────────────────┐
│ 第一层  交互层                                            │
│ AI 对话 · 资料与记忆管理 · 计划与成长 · 情报与机会展示      │
│ 后续：Windows 悬浮球 / 托盘 / 系统通知                     │
├──────────────────────────────────────────────────────────┤
│ 第二层  应用服务层                                        │
│ 请求理解 · 用例编排 · 权限与校验 · 流程调度                 │
├──────────────────────────────────────────────────────────┤
│ 第三层  业务模块层                                        │
│ ┌────────────────┐ ┌────────────────┐                    │
│ │ B1 个人知识库  │ │ B2 个人助理与  │                    │
│ │ 与长期记忆     │ │ 成长管理       │                    │
│ └────────────────┘ └────────────────┘                    │
│ ┌────────────────┐ ┌────────────────┐                    │
│ │ B3 情报与机会  │ │ B4 系统管理与  │                    │
│ │ 发现           │ │ 扩展           │                    │
│ └────────────────┘ └────────────────┘                    │
├──────────────────────────────────────────────────────────┤
│ 第四层  AI 能力层                                         │
│ 对话 · 摘要 · 嵌入检索 · 结构化抽取 · 个性化分析           │
│ 统一接口 + 供应商适配器，业务模块不直接绑定模型            │
├──────────────────────────────────────────────────────────┤
│ 第五层  数据访问层                                        │
│ 仓储 · 查询 · 索引 · 迁移 · 事务                          │
├──────────────────────────────────────────────────────────┤
│ 第六层  存储层                                            │
│ SQLite 结构化数据 · 本地文件 · 索引数据                    │
└──────────────────────────────────────────────────────────┘

横向基础能力（贯穿各层）：
配置管理 · 日志与错误处理 · 定时调度 · 通知管理
数据备份与恢复 · 安全与隐私控制
```

### 2.2 各层职责

| 层 | 职责 | 明确不做什么 |
| --- | --- | --- |
| 第一层 交互层 | 提供界面与入口：对话、资料与记忆管理、计划与成长、情报展示；后续承接桌面入口 | 不包含业务规则，不直接访问数据库或模型 |
| 第二层 应用服务层 | 理解请求、编排流程、做参数与权限校验、协调各层完成一次用例 | 它不是 AI 本身，不实现模型能力，也不承载领域规则 |
| 第三层 业务模块层 | 承载四个业务模块的领域逻辑与数据边界 | 不直接操作数据库文件，不直接调用模型 SDK |
| 第四层 AI 能力层 | 提供可复用的 AI 能力，屏蔽供应商差异 | 不保存业务数据，不做业务判断 |
| 第五层 数据访问层 | 统一的数据读写、查询、索引与迁移入口 | 不包含业务规则，不感知界面 |
| 第六层 存储层 | 实际持久化：SQLite 数据库、本地文件、可重建索引 | 不包含逻辑 |

### 2.3 六层如何协作

以「根据我最近的状态，帮我调整下周计划」为例：

```text
交互层：接收自然语言请求
  → 应用服务层：识别意图为「计划调整」，拆分步骤
      → 业务模块层（B1）：读取近期状态、目标与相关记忆
      → 业务模块层（B2）：读取现有计划与任务执行情况
      → AI 能力层：基于上述上下文生成调整建议
      → 业务模块层（B2）：校验建议、写入新计划
      → 数据访问层 → 存储层：持久化变更
  → 交互层：展示调整结果与建议依据
```

关键点：

- 应用服务层负责**编排**，业务模块负责**判断**，AI 能力层负责**生成**，三者职责不重叠。
- 所有个人上下文都经 B1 的上下文接口获取，其他模块不直接读 B1 的数据表。

### 2.4 分层约束

1. 上层只能依赖下层，禁止反向依赖。
2. 业务模块之间通过明确定义的接口交互，不直接访问彼此的数据表。
3. AI 调用统一走 AI 能力层，业务模块不持有模型 SDK 客户端。
4. 数据访问统一经第五层，任何层都不直接操作 SQLite 文件。
5. 横向能力通过依赖注入或显式参数使用，不形成隐式全局状态。

### 2.5 部署形态：模块化单体

- 六层是**逻辑分层，不是六个独立服务**。
- 首版采用**模块化单体**：一个进程、一个数据库、按目录与接口划分模块。
- 不采用微服务、不做服务注册与网络调用；个人项目没有相应收益，只会增加运维成本。
- 保留未来拆分的可能：模块内部通过接口隔离，边界清晰即可，不提前抽象。

## 3. 四个业务模块在第三层的落地

| 模块 | 内部子能力 | 依赖 | 首版 |
| --- | --- | --- | --- |
| B1 个人知识库与长期记忆 | 个人资料管理、知识库文件管理、记忆提取与分级、检索、来源追溯、个人上下文服务 | 数据访问层、AI 能力层（抽取与嵌入） | 完整交付 |
| B2 个人助理与成长管理 | 对话、状态理解、目标管理、计划与任务、提醒、成长档案、阶段复盘 | B1 上下文接口、AI 能力层 | 仅对话子能力 |
| B3 情报与机会发现 | 信息采集、清洗去重、分类摘要、个性化筛选、机会匹配、简报生成 | B1 上下文接口、AI 能力层、调度能力 | 不包含 |
| B4 系统管理与扩展 | 配置、模型设置、备份恢复、日志审计、健康检查、扩展点 | 数据访问层、横向能力 | 最小配置与备份 |

### 3.1 模块内子能力的组织方式

- 子能力先作为**模块内部服务**实现，通过模块内接口协作。
- 只有跨模块使用的能力才提升为公共接口（如 B1 的个人上下文服务）。
- 合并模块（B2、B3）内部按子域分别建模：计划数据与成长档案分表，新闻条目与机会条目分表。

### 3.2 模块依赖约束

1. B2、B3 只能通过 B1 的「个人上下文服务」获取个人数据，禁止直接读 B1 的表。
2. B2 与 B3 之间不直接依赖；跨模块协作由应用服务层编排。
3. B4 不承载业务规则，不被业务模块反向依赖其内部实现。
4. 核心流程不得依赖任何可选扩展。

## 4. 模块之间如何共享个人记忆

个人记忆的共享采用「**单一数据源 + 只读上下文接口**」模式：

```text
B2 / B3 / 应用服务层
        │  请求：当前任务需要哪些个人上下文
        ▼
B1 个人上下文服务
        │  1. 解析请求（主题、时间范围、需要的记忆类型）
        │  2. 检索知识库与长期记忆
        │  3. 过滤未确认的 AI 推断
        │  4. 按最小必要原则裁剪
        ▼
返回：上下文片段 + 来源标识 + 置信状态
```

规则：

- **只读**：B2、B3 不能通过该接口修改记忆；写入必须走 B1 的记忆管理流程。
- **最小必要**：接口按任务需要返回片段，不返回全量个人数据。
- **标注状态**：返回的每条事实都带「用户提供 / 用户确认 / AI 推断（待确认）」状态；临时上下文不属于长期记忆，不参与跨会话检索。
- **可追溯**：上下文片段附带来源 ID，供最终回答标注引用。
- **可替换**：接口定义稳定后，内部检索实现（关键词 → 语义）可以替换而不影响调用方。

## 5. 关键执行流程

### 5.1 用户对话请求（首版核心流程）

```text
用户输入
  → 交互层：接收消息、基础校验
  → 应用服务层：识别意图、决定是否需要个人上下文
  → B1 上下文服务：按需检索记忆与知识库（仅返回必要片段）
  → AI 能力层：拼装提示词、调用云端模型
  → 结果处理：
      · 标注引用来源
      · 识别到新的个人事实 → 生成「待确认」候选，不直接入库
      · 仅当前会话有效的设定 → 标记为临时上下文，不写入长期记忆
      · 命中敏感信息规则 → 拦截并提示
  → 数据访问层：保存对话记录与候选事实
  → 交互层：展示回答、来源与待确认提示
```

### 5.2 定时任务（提醒与简报，阶段 5 起）

```text
调度器触发（定时 / 条件满足）
  → 应用服务层：分派任务并做幂等校验
  → B2：生成提醒或建议
  → B3：执行采集、去重、筛选、匹配，生成简报
  → 通知管理：按频次与免打扰规则决定是否推送
  → 交互层：通知中心展示
  → 记录执行结果与失败原因
```

### 5.3 外部信息采集（阶段 6 起）

```text
配置的来源清单
  → 采集器拉取原始条目（限流、重试、失败隔离）
  → 清洗、去重、分类、摘要
  → 结合 B1 个人画像判断相关性与匹配度
  → 写入结构化条目（保留来源 URL、抓取时间、原文摘要）
  → 按规则进入简报或提醒
```

### 5.4 记忆写入与事实确认（首版核心流程）

```text
来源：用户明示 / 资料导入抽取 / AI 对话推断
  → 生成事实候选（内容、来源、时间、置信度、状态）
  → 状态判定：
      · 用户直接提供 → 用户提供
      · AI 推断或资料推测 → AI 推断（待确认）
  → 用户操作：
      · 确认 → 转为「用户确认」，可用于上下文
      · 修改 → 更新内容并记录变更
      · 删除 → 标记失效，保留审计记录
  → 删除来源资料时，由其派生的记忆与索引同步失效
```

### 5.5 四类信息状态与生命周期

| 状态 | 定义 | 来源 | 生命周期与处理规则 |
| --- | --- | --- | --- |
| 用户提供 | 用户明确输入或导入的信息 | 手动录入、资料导入 | 可长期保存，由用户直接修改或删除 |
| 用户确认 | 用户已经确认的记忆或事实 | 用户确认的候选事实 | 长期有效，可作为确定事实进入上下文 |
| AI 推断 | AI 根据现有信息推测的内容 | 对话抽取、资料推测 | 默认「待确认」，未确认前不得作为确定事实使用；用户否认则标记失效 |
| 临时上下文 | 仅在当前会话或当前任务中有效的信息 | 当次对话、当次任务设定 | 默认不写入长期记忆；会话或任务结束后不参与检索与跨会话上下文 |

规则：

1. **临时上下文不等于长期记忆**：它不进入记忆库，也不参与跨会话的个人画像构建。
2. 临时上下文若需长期保留，必须由用户明确要求，转为记忆候选并标记「待确认」，经确认后才写入。
3. 任何状态的信息都不能绕过确认流程直接升级为「用户确认」。
4. 删除临时上下文的载体（会话或任务）时，不产生长期记忆残留。

## 6. 技术选型（建议方案）

> 以下为建议技术路线，**尚未完成技术初始化**，不代表已安装或已配置。

### 6.1 核心路线

| 技术 | 是什么 | 在本项目负责什么 | 为什么选择 | 什么时候使用 |
| --- | --- | --- | --- | --- |
| TypeScript | JavaScript 的类型化超集 | 全部业务代码的主要语言，统一前后端类型 | 类型能显著降低 AI 辅助开发中的低级错误；生态成熟 | 阶段 2 起全程 |
| Node.js | JavaScript 运行时 | 运行本地服务端逻辑、数据访问、AI 调用 | 与前端同语言，减少上下文切换；生态完整 | 阶段 2 起 |
| React | 前端 UI 库 | 对话、记忆管理、计划、情报等界面 | 生态最大、资料最多，AI 辅助生成质量高 | 阶段 2 起 |
| Vite | 前端开发与构建工具 | 本地开发服务器、打包 | 启动快、配置少，适合个人项目 | 阶段 2 起 |
| SQLite | 嵌入式关系型数据库 | 本地结构化数据存储（资料、记忆、计划、配置） | 单文件、零运维、易备份，适合单机应用 | 阶段 2 起 |
| 轻量 ORM | 数据库访问封装 | 定义数据模型、执行查询与迁移 | 减少手写 SQL 出错；比全功能 ORM 更轻 | 阶段 2 起（建议 Drizzle 或 Prisma，待确认） |
| 云端 AI API | 外部大模型服务 | 对话、摘要、抽取、后续的嵌入与推荐 | 无需本地算力，效果稳定，按量付费 | 阶段 2 接入接口，阶段 4 正式使用 |
| Electron | 桌面应用框架 | 阶段 7 把 Web 应用封装为 Windows 桌面程序 | 复用现有 Web 技术栈，系统集成能力成熟 | 阶段 7 |
| Git + GitHub | 版本管理与远程备份 | 代码与文档版本管理、远程同步 | 事实标准，便于回溯与多机开发 | 全程 |
| TRAE | AI 辅助编程工具 | 需求拆解、代码生成与修改辅助 | 项目主要开发方式 | 全程 |

### 6.2 建议方案（待确认）

| 领域 | 建议方案 | 说明 |
| --- | --- | --- |
| 后端框架 | Fastify（建议）或 Express | 轻量、插件生态好；NestJS 结构完整但对个人项目偏重 |
| ORM | Drizzle（建议）或 Prisma | Drizzle 更贴近 SQL、类型推导好；Prisma 工具链更完整 |
| 测试框架 | Vitest | 与 Vite 同源，配置成本低 |
| 包管理器 | pnpm（建议）或 npm | pnpm 磁盘效率高；npm 无需额外安装 |
| 向量检索 | 首版不做，后续评估 SQLite 扩展 | 首版以关键词检索为主，语义检索待验证需求 |
| 桌面壳 | Electron（建议） | 与 Web 技术栈一致；Tauri 更轻但引入 Rust 技术栈 |

### 6.3 开发顺序

1. **第一阶段：本地 Web 应用**——前后端均在本机运行，浏览器访问，先验证功能与数据模型。
2. **第二阶段：Electron 封装**——核心功能稳定后，再引入主进程、托盘、通知与开机自启。

理由：桌面封装会引入进程通信、打包、升级等额外复杂度，在功能未稳定前做会放大返工成本。

## 7. 本地存储与数据

### 7.1 存储组成

| 组成 | 内容 | 说明 |
| --- | --- | --- |
| SQLite 数据库 | 个人资料、记忆、知识库元数据、对话、计划、情报条目、配置 | 单文件，便于备份 |
| 本地文件目录 | 用户导入的文档、附件、原始资料 | `data/` 下按类别分目录，不提交到 Git |
| 索引数据 | 全文索引、后续的向量索引 | 派生数据，可随时重建 |
| 日志与审计 | 运行日志、错误日志、事实变更记录 | 滚动写入，避免无限增长 |

### 7.2 数据分类

| 类别 | 内容 | 归属模块 |
| --- | --- | --- |
| 个人资料 | 基本信息、经历、偏好、目标 | B1 |
| 知识库数据 | 文档元数据、笔记、附件引用 | B1 |
| 记忆数据 | 事实、偏好、来源、确认状态、时间 | B1 |
| 对话数据 | 消息、上下文快照、引用来源 | B2 |
| 计划与成长数据 | 目标、计划、任务、成长记录 | B2 |
| 情报与机会数据 | 新闻条目、机会条目、匹配结果 | B3 |
| 配置与密钥引用 | 模型设置、用户偏好、密钥存储位置 | B4 |
| 日志与审计 | 运行日志、错误、变更记录 | B4 |

### 7.3 存储原则

- 原始数据本地优先，不上传完整知识库。
- 索引属于派生数据，删除原始数据后必须同步失效并可重建。
- 数据库变更必须有迁移脚本，不允许直接手改生产数据。
- 备份需覆盖数据库与文件目录，并保证两者一致。

## 8. 云端 AI 调用与隐私控制

### 8.1 基本原则

1. 个人原始数据优先保存在本地。
2. 不默认将完整个人知识库发送给云端模型。
3. 只向云端模型提供当前任务所需的最小上下文。
4. 身份证号、密码、银行卡号等敏感信息默认禁止发送。
5. 重要个人信息的云端传输应可由用户控制。
6. API Key 不得写入前端代码，不得提交到 GitHub。
7. 用户拥有个人数据的查看、修改、导出和删除权。
8. AI 推断的信息不能直接作为确定事实。
9. 重要记忆尽可能保留来源和时间信息。

### 8.2 上下文裁剪策略

```text
任务请求 → 确定所需记忆类型 → 检索候选 → 状态过滤（排除未确认推断）
        → 敏感字段脱敏/拦截 → 条数与时长的上限裁剪 → 组装提示词
```

- 首版即建立裁剪逻辑，不能等数据量变大再补。
- 裁剪规则集中配置，不散落在各业务模块。
- 每次调用记录「发送了哪些片段」，便于用户事后查看。

### 8.3 敏感信息处理

- 建立敏感字段识别规则（证件号、银行卡、密码、私钥等）。
- 命中规则时默认阻断发送，并向用户说明原因。
- 日志中不得记录完整的提示词与个人敏感内容，只记录调用元信息。

## 9. AI 统一调用接口

### 9.1 能力抽象

AI 能力层至少抽象以下能力，各自定义统一接口：

| 能力 | 用途 | 首版 |
| --- | --- | --- |
| 对话生成 | 多轮对话与问答 | 是 |
| 文本摘要 | 资料摘要、长文压缩 | 是（轻量使用） |
| 结构化抽取 | 从对话与资料中抽取事实候选 | 是 |
| 嵌入与检索 | 语义检索、相似度匹配 | 否，后续评估 |
| 个性化分析 | 相关性判断、机会匹配、建议生成 | 否，阶段 5/6 |

### 9.2 接口设计要求

- 业务模块只依赖能力接口，不依赖具体供应商 SDK。
- 每个能力接口包含：输入、输出、超时、重试、错误类型。
- 供应商适配器负责鉴权、请求格式转换、错误映射。
- 所有调用统一记录：模型、耗时、token 用量、估算成本、是否成功。
- 支持通过配置切换供应商与模型，无需改业务代码。

### 9.3 失败与降级

- 模型不可用时，对话应明确提示失败原因，而不是返回空结果。
- 涉及个人上下文的调用失败时，不得退化为「无上下文直接回答」而不告知用户。
- 重试有上限，失败任务进入队列等待，不阻塞主流程。

## 11. 首版实现范围与后续范围

### 11.1 首版（阶段 2–4）

- 本地 Web 应用骨架（Node.js 服务 + React 前端）。
- SQLite 数据库、数据访问层、迁移脚本。
- 配置管理、日志与错误处理。
- AI 统一调用接口 + 一个云端模型适配器。
- B1：个人资料、知识库、长期记忆、检索、来源追溯、上下文服务。
- B2：AI 对话（含上下文调用、来源标注、敏感信息拦截）。
- B4：最小配置与备份能力。

### 11.2 后续（阶段 5–8）

- 计划、任务、提醒、状态分析与成长档案（B2）。
- 情报采集、简报与机会匹配（B3）。
- 定时调度与通知的完整能力。
- Electron 桌面化、托盘、系统通知、后台运行。
- 备份恢复完善、健康检查、扩展点。

## 12. 刻意不采用的设计

| 不采用 | 原因 |
| --- | --- |
| 微服务 / 服务网格 | 单用户桌面应用无收益，增加部署与调试成本 |
| 独立向量数据库 | 首版数据量小，关键词检索足够；按需再评估 |
| 大型 RAG 框架 | 引入黑盒复杂度，个人项目更需要可读可控的实现 |
| 本地运行大模型 | 硬件成本高，首版使用云端 API |
| 插件沙箱与市场 | 首版无第三方扩展需求，只预留扩展点 |
| 多用户权限体系 | 单用户自用，无此需求 |
| 多端同步服务 | 不在当前定位内，且会显著增加复杂度 |

## 13. 架构层面的待确认事项

1. 后端框架最终选择（Fastify / Express / 其他）。
2. ORM 最终选择（Drizzle / Prisma / 原生 SQL）。
3. 云端模型供应商、模型版本与成本上限。
4. 首版检索方式：仅关键词，还是引入本地向量检索。
5. 密钥存储方式（系统凭据管理器 / 加密配置文件）。
6. 备份位置、加密方式与恢复粒度。
7. Electron 主进程与本地服务的通信方式（进程内调用 / 本地端口）。
8. 测试策略与覆盖率要求。
9. 日志保留周期与审计范围。
