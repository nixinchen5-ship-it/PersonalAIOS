# PersonalAIOS 项目计划

> 文档状态：第三版（产品模块调整为四个）
> 最后更新：2026-11-20
> 说明：本文档只描述产品定位、业务模块、需求范围与开发阶段。技术实现见 [technical-architecture.md](./technical-architecture.md)。凡未确认内容均标注「待确认」，不得作为实现依据。

## 1. 项目背景

个人在长期学习与工作中积累的信息、经历、目标与偏好，通常分散在笔记、文档、聊天记录、待办工具和资讯平台之间：

- 通用 AI 聊天工具缺少对个人的长期了解，每次对话都要重新交代背景。
- 任务与计划工具只管理待办，无法结合个人经历判断什么值得做。
- 资讯与招聘平台内容过载，无法按个人情况筛选，实际机会容易错过。

PersonalAIOS 是面向个人使用、长期运行的 Windows 桌面 AI 助理系统。它不是普通聊天机器人，也不只是任务管理或资讯聚合工具，而是通过持续积累个人上下文，在知识、行动和外部信息三个方向上提供长期辅助。

核心价值：**持续了解我、记录我、辅助我做决策，并主动为我发现有价值的信息和机会。**

## 2. 产品定位与边界

### 2.1 定位

| 维度 | 定位 |
| --- | --- |
| 使用范围 | 单用户自用，不设计多用户、团队协作与账号权限体系 |
| 运行形态 | Windows 桌面应用，长期常驻后台；首版先以本地 Web 应用开发，功能稳定后封装为桌面应用 |
| 使用周期 | 长期运行、持续积累、持续演进，而非一次性会话工具 |
| 认知基础 | 个人知识库与长期记忆是其他所有业务能力的输入前提 |
| 交互方式 | 自然语言对话为主，配合资料管理与后续的桌面入口（悬浮球、托盘、系统通知） |
| 主动性 | 在受控频率下主动提醒与推送，不打扰、不过载 |

### 2.2 当前阶段的非目标

- 不做多用户、团队协作、账号与权限体系。
- 不做公开内容发布平台或社交功能。
- 首版不做计划管理、成长管理、情报与机会发现（属后续阶段）。
- 首版不做 Windows 桌面封装（阶段 7 再做），先以本地 Web 应用验证功能。
- 不做复杂插件市场、第三方插件沙箱和多人权限系统，只为扩展预留空间。
- 暂不要求本地运行大型模型，AI 能力通过云端 API 提供。
- 多设备同步不在当前定位内（是否作为远期目标待确认）。

## 3. 项目目标与成功标准

| 编号 | 目标 | 说明 | 阶段 |
| --- | --- | --- | --- |
| G1 | 建立可持续演进的项目骨架 | 文档、规范、目录先行 | 已完成 |
| G2 | 建立个人知识库与长期记忆 | 记录、检索、确认、追溯、提供个人上下文 | 首版 MVP |
| G3 | 基于个人上下文提供 AI 对话 | 能调用记忆与知识库作答并标注来源 | 首版 MVP |
| G4 | 计划、成长与外部情报辅助 | 计划任务、成长档案、情报简报、机会匹配 | 后续阶段 |
| G5 | 数据可控、可备份、可恢复 | 用户拥有查看、修改、导出、删除权 | 持续要求 |
| G6 | 形成稳定的 Windows 桌面形态 | 常驻、托盘、通知、后台运行 | 阶段 7 |

### 3.1 成功标准（定性）

首版达到以下状态即视为成功：

1. 能基于个人资料与记忆回答「我以前做过什么、我的偏好是什么」，并给出可追溯来源。
2. 每条 AI 推断出的个人事实都带「待确认」标记，未经确认不会被当作确定事实使用。
3. 记忆的新增、查看、修改、删除可完整执行，删除后检索结果同步更新。
4. AI 对话默认只发送当前任务所需的最小上下文，而非全量个人数据。
5. 首版三项能力（知识库、长期记忆、AI 对话）通过 [module-acceptance.md](./module-acceptance.md) 的专项验收。

> 待确认：是否需要量化指标（如检索命中率、对话引用准确率、每日使用时长）。

## 4. 核心设计原则

1. **个人知识库与长期记忆是系统的认知基础**，其他业务模块按需调用。
2. **模块职责独立**，但可以共享底层能力（AI、数据访问、调度、通知）。
3. **AI 模型与外部服务尽可能可替换**，业务模块不绑定具体供应商。
4. **AI 不能把自己的推断直接当成用户明确表达的事实**。
5. **个人原始数据优先本地保存**，不默认上传完整知识库。
6. **云端 AI 只接收当前任务所需的必要上下文**。
7. **数据可查看、修改、导出、删除**，用户拥有个人数据的管理权。
8. **架构优先简单、可靠、可维护**，不过度设计。
9. **每个开发阶段都必须实际测试和验收**，不接受「功能正常」这类不可验证的说法。
10. **新功能不能随意破坏已有功能**，改动需评估对既有模块的影响。

## 5. 核心需求与首版 MVP

### 5.1 首版 MVP（已确认）

首版只重点开发三项核心能力，其余功能不进入首版验收范围。

| 能力 | 首版包含 | 归属 |
| --- | --- | --- |
| 个人知识库 | 个人信息的录入与修改；资料/笔记导入与保存；基础检索；来源追溯 | 模块一 |
| 长期记忆 | 从对话与资料中提取记忆；区分用户事实与 AI 推断；查看、确认、修改、删除 | 模块一 |
| AI 对话 | 自然语言问答；按需调用个人记忆与知识库；标注引用来源；信息不足时主动询问 | 模块二（对话子能力） |

同时随基础底座提供：必要配置管理、日志与错误处理、基础数据备份、隐私与数据管理的最小机制。

### 5.2 首版明确不做

- 计划、任务、日历、定时提醒。
- 个人状态分析、目标管理、成长档案、阶段复盘。
- 新闻采集、每日简报、趋势分析。
- 实习/招聘/比赛/活动等机会发现与匹配。
- 悬浮球、托盘、系统通知等桌面形态（阶段 7 实现）。
- 插件市场、第三方扩展沙箱。

### 5.3 后续需求

| 需求 | 归属模块 | 计划阶段 |
| --- | --- | --- |
| 计划、任务、提醒、状态分析 | 模块二 | 阶段 5 |
| 成长档案、能力追踪、阶段复盘 | 模块二 | 阶段 5 |
| 新闻情报采集、清洗、简报、趋势分析 | 模块三 | 阶段 6 |
| 城市实习/招聘/活动机会发现与匹配 | 模块三 | 阶段 6 |
| Windows 桌面化、托盘、通知、后台运行 | 交互层 | 阶段 7 |
| 备份恢复、系统健康检查、扩展能力 | 模块四 | 阶段 8 |

## 6. 业务模块规划

> 本节描述的是**产品功能架构**，与 [technical-architecture.md](./technical-architecture.md) 中的六层技术架构是两个不同维度，不要混用。

### 6.1 模块总览

| 编号 | 模块 | 定位 | 首版范围 | 状态 |
| --- | --- | --- | --- | --- |
| B1 | 个人知识库与长期记忆 | 系统认知基础 | 核心，完整交付 | 未开始 |
| B2 | 个人助理与成长管理 | 核心业务 | 仅 AI 对话子能力 | 未开始（首版包含 AI 对话最小范围） |
| B3 | 情报与机会发现 | 核心业务 | 不包含 | 规划中 |
| B4 | 系统管理与扩展 | 支撑 | 仅最小配置、日志与备份能力 | 未开始（首版包含最小配置、日志与备份能力） |

### 6.2 模块一：个人知识库与长期记忆

**定位**：整个系统的个人认知基础，所有其他模块的个人上下文都来源于此。

**主要功能**：

1. 记录用户主动提供的个人信息、经历、偏好和目标。
2. 保存用户上传的文件、笔记和个人资料。
3. 建立个人画像（基本背景、兴趣、职业方向、长期目标）。
4. 提取并管理长期有价值的个人记忆。
5. 支持自然语言检索个人历史信息。
6. 为其他业务模块提供相关个人上下文。
7. 支持记忆查看、确认、修改、删除和来源追溯。
8. 区分用户提供、用户确认、AI 推断和临时上下文四类信息状态（定义见本节「四类信息状态」表）。

**需要区分的数据概念（不允许混在同一列表中）**：

| 概念 | 定义 | 示例 |
| --- | --- | --- |
| 长期记忆 | 关于用户、长期有效的结论性信息 | 「偏好远程岗位」「目标城市是杭州」 |
| 知识库 | 用户保存的文档、资料、笔记及其元数据 | 简历、课程笔记、项目文档 |
| 计划数据 | 用户准备做什么、何时做、是否完成 | 本周计划、待办事项 |
| 成长档案 | 用户的经历、项目、技能与能力变化 | 实习经历、技能掌握程度 |

四者可以互相关联（例如一条成长档案可引用某份资料），但存储结构、生命周期和修改权限不同，必须分别建模。

**四类信息状态（与上述数据类型正交，可作用于任意一类数据）**：

| 信息状态 | 定义 | 是否写入长期记忆 |
| --- | --- | --- |
| 用户提供 | 用户明确输入或导入的信息 | 可写入，由用户直接管理 |
| 用户确认 | 用户已经确认的记忆或事实 | 写入，可作为确定事实使用 |
| AI 推断 | AI 根据现有信息推测的内容 | 仅以「待确认」状态暂存，确认后才可写入 |
| 临时上下文 | 仅在当前会话或当前任务中有效的信息 | 默认不写入 |

**边界**：不负责计划推进（属模块二），不负责外部信息采集（属模块三）。

### 6.3 模块二：个人助理与成长管理

**定位**：根据用户当前情况，帮助用户规划生活、推动目标并观察成长。原「个人助理与计划管理」与「个人成长中心」合并为本模块。

#### A. 计划与任务管理

- 制定每日、每周、每月计划。
- 通过自然语言创建和管理任务。
- 记录任务完成情况与执行进度。
- 提供定时提醒。
- 根据用户实际状态调整计划。

#### B. 个人状态与目标管理

- 记录当前阶段的状态、目标和重点事项。
- 结合近期执行情况分析计划是否合理。
- 根据实际情况提出调整建议。
- 追踪长期目标与阶段性目标。

#### C. 成长档案与能力追踪

- 记录学习、工作、项目和实践经历。
- 建立个人技能与能力档案。
- 追踪能力变化与成长轨迹。
- 定期生成阶段性成长报告。
- 识别优势、短板与下一阶段发展方向。

#### D. AI 个性化建议

- 结合长期记忆、近期状态、目标和历史执行情况提出建议。
- 依据真实情况判断，而不是生成通用模板。
- 信息不足时主动询问，不凭空推断。

**首版范围**：仅交付 D 中的「AI 对话」最小形态——能调用模块一的记忆与知识库回答用户问题，不做主动建议、不做计划生成。

**边界**：不直接存储外部资讯与机会（属模块三）；个人上下文不自行落库，统一从模块一获取。

### 6.4 模块三：情报与机会发现

**定位**：持续获取外部信息，结合个人画像进行筛选、分析和推荐。原「情报雷达」与「城市机会发现」合并为本模块。

#### A. 情报雷达

- 定期收集 AI、科技、商业及其他关注领域的新闻。
- 支持中英文信息来源。
- 对信息进行清洗、去重、分类和摘要。
- 根据兴趣、目标和职业方向判断相关性。
- 生成每日或定期信息简报。
- 分析重要事件与行业趋势。
- 结合个人知识库解释信息对用户的意义。

#### B. 城市与发展机会

- 定期收集不同城市的实习、招聘和工作机会。
- 收集比赛、训练营、行业活动、线下交流和城市资源信息。
- 根据用户经历、能力、兴趣和目标进行匹配。
- 支持按城市、岗位、行业、时间等条件筛选。
- 对机会进行相关性排序。
- 记录感兴趣的机会与后续申请进度。

**两者共用**：信息采集、清洗、去重、分类、筛选与个性化分析能力。

**两者必须分别设计**：数据结构、来源管理、筛选规则、展示方式。

**核心区别**：

- 情报方向回答：发生了什么？哪些信息值得关注？
- 机会方向回答：有什么机会？哪些适合我？下一步可以做什么？

**边界**：不存储个人资料与长期记忆（属模块一）；不负责用户计划执行（属模块二）。

### 6.5 模块四：系统管理与扩展

**定位**：保障整个系统安全、稳定、长期运行。

**主要功能**：

- AI 模型及 API 配置。
- 用户隐私与数据传输控制。
- 数据备份、恢复和导出。
- 系统日志与错误管理。
- 系统运行状态检查。
- 定时任务与通知的基础管理。
- 未来支持外部工具和插件扩展。

**边界**：不承载业务规则，只提供基础设施与系统级能力。初期不实现复杂插件市场、第三方插件沙箱和多人权限系统，仅保留合理的扩展空间。

### 6.6 模块之间的关系

**模块一是整个系统的个人认知基础**，其他业务模块按需读取相关个人信息：

- 模块二：读取目标、习惯、近期状态和历史成长记录。
- 模块三：读取兴趣、职业方向、技能和城市偏好。
- 模块四：管理这些数据的安全、存储、备份和使用权限。

```text
                    应用服务层（请求理解与流程编排）
                              │
        ┌─────────────────────▼─────────────────────┐
        │  B1 个人知识库与长期记忆（认知基础）        │
        │  个人信息 · 资料 · 长期记忆 · 来源追溯      │
        └──────┬───────────────────────┬────────────┘
   个人上下文接口                     个人上下文接口
        ┌──────▼──────────┐   ┌────────▼────────────┐
        │ B2 个人助理与    │   │ B3 情报与机会发现    │
        │ 成长管理         │   │                     │
        └──────────────────┘   └─────────────────────┘

  B4 系统管理与扩展：横向提供配置、安全、备份、日志、扩展能力，不参与业务逻辑
```

**依赖约束**：

1. 模块二、模块三不直接读写模块一的数据表，只通过模块一的「个人上下文服务」接口获取数据。
2. 模块二与模块三之间不直接依赖；需要共享的信息由模块一提供，或经应用服务层编排。
3. 模块四不包含业务判断逻辑，只提供基础设施能力。
4. 模块合并只是产品层面的归类，**不意味着数据表合并**：计划数据、成长档案、新闻条目、机会条目仍各自独立建模。

### 7.2 各阶段说明

#### 阶段 0：项目初始化（已完成）

- 阶段目标：建立可持续演进的项目骨架。
- 主要功能：目录结构、四份项目文档、`.gitignore`、Git 仓库与远程同步。
- 前置依赖：无。
- 交付物：`docs/`、`src/`、`data/`、`tests/` 目录骨架与初始文档。
- 验收标准：目录结构符合约定；文档齐备；无业务代码与依赖。
- 当前状态：已完成，验收记录见 [module-acceptance.md](./module-acceptance.md)。

#### 阶段 1：产品需求与技术架构确认（进行中）

- 阶段目标：把产品定位、模块边界、首版范围、技术选型从「草案」变为「确认」。
- 主要功能：确认四模块边界与数据边界；确认首版三项能力的可执行判定条件；确认技术路线与桌面壳方案；确认隐私与云端数据边界。
- 前置依赖：阶段 0。
- 交付物：修订后的项目计划、技术架构、开发规范与验收标准；技术选型决策记录。
- 验收标准：文档间无冲突；所有关键「待确认」项有结论或明确延后；首版验收标准可逐条测试。
- 当前状态：进行中（本次修订完成后进入待确认）。

#### 阶段 2：基础底座（未开始）

- 阶段目标：搭建可运行、可测试的最小工程底座。
- 主要功能：项目框架与构建；配置管理；日志与统一错误处理；SQLite 数据库与迁移；数据访问层；AI 统一调用接口（可先接一个云端模型）。

## 8. 已确认事项

| 编号 | 事项 | 结论 |
| --- | --- | --- |
| C1 | 使用范围 | 单人自用，不做多用户 |
| C2 | 运行平台 | Windows 桌面，先本地 Web 应用后 Electron 封装 |
| C3 | 产品架构 | 四个核心业务模块，模块一为认知基础 |
| C4 | 技术架构 | 六层逻辑架构，模块化单体，非微服务 |
| C5 | 首版范围 | 个人知识库 + 长期记忆 + AI 对话 |
| C6 | 技术路线 | TypeScript / Node.js / React / Vite / SQLite / 云端 AI API / Electron |
| C7 | 数据原则 | 原始数据本地优先，云端只接收最小上下文 |
| C8 | 事实原则 | AI 推断必须标记，未经确认不得作为确定事实 |
| C9 | 开发节奏 | 阶段 0–8，每阶段验收后才推进 |
