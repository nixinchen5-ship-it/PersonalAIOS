# PersonalAIOS 开发规范

> 文档状态：第二版（对齐四模块与技术路线）
> 最后更新：2026-11-20
> 适用范围：本仓库全部代码、文档与提交记录。本文档是开发约定，**不代表现在就要安装 ESLint、Prettier 或其他工具**；工具配置与具体规则集标注「待确认」。

## 1. 通用原则

1. **可读性优先**于技巧性，代码以「他人能快速理解」为标准。
2. **小步提交**，单次改动聚焦一个问题。
3. **依赖克制**：不引入未评审的依赖，新增依赖需说明用途与替代方案。
4. **不提交**调试代码、注释掉的大段代码、临时文件。
5. **未确认的方案不落地**：技术选型与产品需求未确认前，不写实现。
6. **改动评估影响**：新功能必须考虑是否影响已有模块，不能默认「改完这里就结束」。

## 2. TypeScript 规范

1. 开启严格模式（`strict: true`），不使用隐式 `any`。
2. 避免随意使用 `any`。确需放宽时使用 `unknown` 并在边界处收窄，或写注释说明原因。
3. 公共函数、对外接口、模块边界必须有明确的参数与返回值类型。
4. 统一类型定义：
   - 领域类型放在模块内的 `types/` 目录。
   - 跨模块共享的类型放在公共类型目录，禁止各模块重复定义同一结构。
   - 从外部接口（AI 响应、文件解析）获得的 JSON 视为不可信数据，必须校验后再使用。
5. 优先使用 `interface` 描述对象结构，使用 `type` 描述联合类型与工具类型。
6. 禁止使用非空断言 `!` 掩盖可能为空的值；必须显式判空。
7. 枚举值优先使用字面量联合类型或 `as const` 对象，避免数字枚举。

> 待确认：是否启用 `noUncheckedIndexedAccess`、`exactOptionalPropertyTypes` 等更严格的编译选项。

## 3. React 规范

1. **组件职责清晰**：一个组件只负责一个界面区块，不承担数据获取、业务计算和展示三件事。
2. **UI 与业务逻辑分离**：
   - 展示组件只接收数据与回调。
   - 数据获取、状态编排、业务判断放在 hooks 或服务层。
3. **避免过度拆分**：不为「复用一次」创建组件；拆分依据是职责与变化频率，不是行数。
4. **状态管理克制**：
   - 优先使用局部状态。
   - 仅在跨组件共享时提升状态或使用轻量状态库。
   - 服务端数据与界面状态分开管理，不混在同一个 store 里。
5. 组件文件使用 `.tsx`，hooks 使用 `use` 前缀，文件名与组件名保持一致。
6. 列表渲染必须提供稳定的 `key`，禁止使用数组下标作为可变列表的 key。
7. 禁止在渲染过程中执行有副作用的操作（请求、写库、修改全局状态）。

> 待确认：状态管理方案（Context / Zustand / Redux）与服务端数据缓存方案。

## 4. Node.js 规范

1. **业务逻辑与基础设施分离**：数据库连接、HTTP 客户端、日志、配置不与业务规则混写。
2. **统一错误处理**：
   - 定义项目统一的错误类型与错误码。
   - 业务错误与系统错误分开表示。
   - 禁止空 `catch`，禁止吞掉异常后继续执行。
3. **异步操作必须处理异常**：所有 `await` 都可能失败，调用方需明确处理或向上抛出。
4. **配置与密钥统一管理**：通过配置模块读取，禁止在业务代码中散落 `process.env` 读取。
5. 文件与网络 I/O 必须设置超时；外部请求必须有失败隔离，不能因单个来源失败拖垮整个流程。
6. 避免阻塞主线程的同步操作；大文件处理采用流式方式。

> 待确认：日志库、HTTP 客户端与错误上报方案。

## 5. Electron 规范（阶段 7 起适用）

1. **主进程与渲染进程职责分离**：
   - 主进程负责窗口、托盘、系统通知、文件系统与系统能力。
   - 渲染进程只负责界面。
2. **优先使用安全的进程通信方式**：通过 `preload` + `contextBridge` 暴露受控 API，禁止渲染进程直接访问 Node.js 能力。
3. **不允许渲染进程随意访问本地文件和系统能力**：每个暴露的能力必须是最小集合，并做参数校验。
4. 关闭 `nodeIntegration`，开启 `contextIsolation`，不关闭安全警告。
5. 外部链接与不可信内容不得在应用内直接加载执行。
6. 窗口、托盘、通知、开机自启等行为必须有明确的启停配置，避免用户无法退出。

> 待确认：Electron 版本、打包工具（electron-builder 等）、自动更新策略。

## 6. 项目架构与模块边界

1. **四个业务模块职责清晰**：B1 个人知识库与长期记忆、B2 个人助理与成长管理、B3 情报与机会发现、B4 系统管理与扩展。
2. **模块之间通过明确接口协作**：禁止跨模块直接引用对方内部文件。
3. **共享能力统一管理**：AI 调用、数据访问、配置、日志、调度、通知作为公共服务，由统一入口提供。
4. **不允许业务模块直接操作底层数据库文件**：所有读写经数据访问层。
5. **业务模块不直接调用模型 SDK**：必须经 AI 能力层。
6. **禁止循环依赖**：出现循环依赖视为设计缺陷，评审时必须修正。
7. **新功能必须评估对已有模块的影响**，涉及共享数据结构变更时需同步更新相关模块与测试。

### 6.1 目录组织建议（待确认）

```text
src/
├── main/            # 服务端入口与进程启动
├── renderer/        # 前端界面（React）
├── modules/         # 业务模块

├── shared/          # 跨模块类型、常量、工具
└── platform/        # 配置、日志、调度、通知、备份
```

## 7. 命名规范

| 对象 | 规范 | 示例 |
| --- | --- | --- |
| 变量 / 函数 | 小驼峰 | `loadConfig` |
| 类 / 类型 / 接口 / 组件 | 大驼峰 | `TaskService`、`MemoryCard` |
| 常量 | 全大写下划线 | `MAX_RETRY_COUNT` |
| 布尔值 | 以 `is` / `has` / `can` 开头 | `isEnabled` |
| 事件处理函数 | `handle` + 事件名 | `handleSubmit` |
| 异步函数 | 动词开头，必要时体现异步语义 | `fetchMemories` |
| 私有成员 | 通过访问修饰符控制，不依赖下划线 | `private cache` |

- 命名使用完整单词，避免无意义缩写（`id`、`url`、`api` 等通用缩写除外）。
- 禁止拼音与英文混用命名。
- 数据库字段使用下划线命名，与代码中的驼峰通过数据访问层映射。

## 8. 文件与目录命名规范

| 类型 | 规范 | 示例 |
| --- | --- | --- |
| 目录 | 小写短横线（kebab-case） | `memory-manager/` |
| 源码文件 | 小写短横线 | `memory-service.ts` |
| React 组件文件 | 大驼峰或小写短横线，项目内统一 | `MemoryCard.tsx` |
| 测试文件 | 与被测文件同名 + `.test` | `memory-service.test.ts` |
| 文档 | 小写短横线 + `.md` | `development-standards.md` |
| 配置文件 | 工具约定名称 | `.gitignore`、`package.json` |
| 资源文件 | 小写短横线 | `logo-dark.svg` |

补充约定：

- 除约定俗成的文件外，文件名不使用大写字母与空格。
- 文件名需能表达内容，禁止 `utils2.ts`、`temp.ts`、`new-file.ts` 之类命名。
- 临时文件不得提交，放入被忽略的目录。

## 9. 注释规范

1. **注释解释「为什么」，不复述「做什么」**。
2. 公共模块、公共函数使用文档注释（TSDoc 风格）：

```ts
/**
 * 加载并校验应用配置。
 * @returns 已校验的配置对象
 * @throws 配置文件缺失或字段非法时抛出
 */
export function loadConfig(): AppConfig {
  // ...
}
```

3. 复杂业务规则、非直觉的边界处理必须写行内注释说明原因。
4. 使用 `TODO:` / `FIXME:` 标记待办，格式为 `TODO(负责人, 日期): 说明`。当前无负责人，可写 `TODO: 说明`。
5. 禁止提交大段注释掉的废弃代码，历史交给版本控制。
6. 中文注释与英文注释均可，但同一文件内保持一致。
7. 文档与代码中的「待确认」必须显式保留，不得以假设内容填充。

## 10. Git 版本管理规范

### 10.1 分支策略（待确认）

| 分支 | 用途 | 说明 |
| --- | --- | --- |
| `main` | 稳定分支 | 保持可运行，禁止直接开发 |
| `feature/<name>` | 功能开发 | 从 `main` 拉出 |
| `fix/<name>` | 缺陷修复 | 从 `main` 拉出 |
| `docs/<name>` | 文档变更 | 从 `main` 拉出 |

> 待确认：单人项目是否需要简化流程，以及是否保留 `develop` 分支。

### 10.2 提交信息

采用 Conventional Commits 风格：

```text
<type>(<scope>): <subject>

<body 可选>
<footer 可选>
```

| type | 含义 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档变更 |
| `refactor` | 重构（不改变行为） |
| `test` | 测试相关 |
| `chore` | 构建、配置、依赖等杂项 |
| `style` | 格式调整（不影响逻辑） |

示例：

```text
docs: refine PersonalAIOS project architecture
```

规则：

- 主题行不超过 50 个字符，使用祈使句，结尾不加句号。
- 一次提交只做一件事。
- 禁止提交无法编译 / 无法运行的中间状态到 `main`。

### 10.3 提交与远程同步

- 提交前自查：无调试代码、无敏感信息、无临时文件。
- 提交前查看 `git diff`，确认改动范围与预期一致。
- 推送前确认本地与远程无分叉；出现分叉时先沟通，不强行覆盖。
- 禁止 `git push --force`、禁止擅自 `reset` 他人提交。

### 10.4 版本管理

- 文档与代码同等纳入版本管理。
- 破坏性数据结构变更必须在提交信息中说明，并附带迁移方案。
- 备份、导出的数据文件不进入 Git。

> 待确认：版本号规则（是否采用 SemVer）、发布流程、是否启用提交钩子校验。

## 11. 终端与换行符

1. 统一使用 LF 换行符。
2. 通过 `.gitattributes` 作为仓库级规范兜底，保证不同操作系统和编辑器下换行符一致（该文件尚未创建，是否创建待确认）。
3. 提交前检查 `git diff`，避免整文件换行符变更掩盖真实改动。
4. 跨平台协作时，避免仅大小写不同的文件名。
5. 不通过修改 Git 全局配置来替代仓库级规范。

## 12. 隐私与安全规范

1. **API Key 不得写入源代码**，也不得出现在前端打包产物中。
2. **不得将敏感个人数据写入普通日志**：证件号、银行卡、密码、私钥、完整对话内容等。
3. **云端 AI 调用遵循最小必要数据原则**：只发送当前任务需要的片段，不发送全量知识库。
4. **敏感字段默认阻断**：命中敏感信息规则时停止发送并提示用户，而不是「脱敏后照发」。
5. **用户数据的删除和备份需保持一致**：删除后，备份、索引、派生数据按既定策略同步处理。
6. **密钥读取统一走配置模块**，优先使用系统凭据存储；配置文件中的密钥仅保存引用。
7. **外部内容不可信**：抓取的网页、导入的文件、模型返回的内容都需校验后再使用，不直接执行。
8. **错误信息不回显敏感内容**：给用户看的错误提示不包含密钥、完整路径或原始个人数据。

> 待确认：敏感字段识别规则的维护方式、日志脱敏粒度、密钥存储最终方案。
