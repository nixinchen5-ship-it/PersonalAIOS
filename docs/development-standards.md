# PersonalAIOS 开发规范

> 文档状态：初稿（项目初始化阶段）
> 最后更新：2026-11-20
> 适用范围：本仓库全部代码、文档与提交记录。规范中的技术细节为约定草案，未确认项标注「待确认」。

## 1. 通用原则

1. 可读性优先于技巧性，代码以「他人能快速理解」为标准。
2. 小步提交、小步合并，单次改动聚焦一个问题。
3. 不引入未评审的依赖；新增依赖需说明理由。
4. 不提交调试代码、注释掉的大段代码、临时文件。
5. 未确认的技术方案不在代码中先行落地。

## 2. 代码规范

以下为通用约定，具体工具链待技术选型确认后补齐。

### 2.1 语言（待确认）

- 初步候选：TypeScript。若最终选型变化，本节随之调整。
- 开启严格模式（`strict`），避免隐式 `any`。
- 公共函数、对外接口必须有明确的类型标注。

### 2.2 命名

| 对象 | 规范 | 示例 |
| --- | --- | --- |
| 变量 / 函数 | 小驼峰 | `loadConfig` |
| 类 / 类型 / 接口 | 大驼峰 | `TaskService`、`UserConfig` |
| 常量 | 全大写下划线 | `MAX_RETRY_COUNT` |
| 布尔值 | 以 `is` / `has` / `can` 开头 | `isEnabled` |
| 私有成员 | 不依赖下划线，通过访问修饰符控制 | `private cache` |

- 命名使用完整单词，避免无意义缩写（业界通用缩写如 `id`、`url` 除外）。
- 禁止拼音与英文混用命名。

### 2.3 格式

- 缩进：2 个空格。
- 行宽：建议不超过 100 字符。
- 字符串：统一使用单引号。
- 语句结尾必须带分号。
- 统一由格式化工具保证（候选：Prettier，待确认）。

### 2.4 代码结构

- 单个文件建议不超过 300 行，超出时考虑拆分。
- 单个函数建议不超过 50 行，职责单一。
- 提前返回（early return）代替深层嵌套，嵌套层级不超过 3 层。
- 禁止魔法数字，提取为具名常量。
- 错误必须被处理或向上抛出，禁止空 `catch`。

### 2.5 依赖与模块

- 模块间通过明确导出交互，禁止跨模块直接访问内部文件。
- 循环依赖视为缺陷，需在评审时修正。

> 待确认：ESLint 规则集、Prettier 配置、是否强制提交前校验（husky + lint-staged）。

## 3. 文件与目录命名规范

| 类型 | 规范 | 示例 |
| --- | --- | --- |
| 目录 | 小写短横线（kebab-case） | `task-manager/` |
| 源码文件 | 小写短横线 | `task-service.ts` |
| 测试文件 | 与被测文件同名 + `.test` | `task-service.test.ts` |
| 文档 | 小写短横线 + `.md` | `development-standards.md` |
| 配置文件 | 工具约定名称 | `.gitignore`、`package.json` |
| 资源文件 | 小写短横线 | `logo-dark.svg` |

补充约定：

- 除约定俗成的文件外，文件名不使用大写字母与空格。
- 文件名需能表达内容，禁止 `utils2.ts`、`temp.ts`、`new-file.ts` 之类命名。
- 临时文件不得提交，放入被忽略的目录。

## 4. 注释规范

1. **注释解释「为什么」，不复述「做什么」**；代码本身应表达做了什么。
2. 公共模块、公共函数使用文档注释（TSDoc / JSDoc 风格）：

```ts
/**
 * 加载并校验应用配置。
 * @returns 已校验的配置对象
 * @throws 配置文件缺失或字段非法时抛出
 */
export function loadConfig(): AppConfig {
  // ...
}
```

3. 复杂业务规则、非直觉的边界处理必须写行内注释说明原因。
4. 使用 `TODO:` / `FIXME:` 标记待办，格式为 `TODO(负责人, 日期): 说明`。当前无负责人，可写 `TODO: 说明`。
5. 禁止提交大段注释掉的废弃代码，历史交给版本控制。
6. 中文注释与英文注释均可，但同一文件内保持一致。
7. 文档中的「待确认」必须显式保留，不得以假设内容填充。

## 5. Git 版本管理规范

### 5.1 分支策略（待确认）

初步建议：

| 分支 | 用途 | 说明 |
| --- | --- | --- |
| `main` | 稳定分支 | 保持可运行，禁止直接推送 |
| `feature/<name>` | 功能开发 | 从 `main` 拉出 |
| `fix/<name>` | 缺陷修复 | 从 `main` 拉出 |
| `docs/<name>` | 文档变更 | 从 `main` 拉出 |

> 待确认：是否需要 `develop` 分支、是否为单人项目简化流程。

### 5.2 提交信息

采用 Conventional Commits 风格：

```text
<type>(<scope>): <subject>

<body 可选>
<footer 可选>
```

常用 `type`：

| type | 含义 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档变更 |
| `refactor` | 重构（不改变行为） |
| `test` | 测试相关 |
| `chore` | 构建、配置、依赖等杂项 |
| `style` | 格式调整（不影响逻辑） |

示例：

```text
docs(project): 初始化项目计划与架构文档
```

规则：

- 主题行不超过 50 个字符，使用祈使句，结尾不加句号。
- 一次提交只做一件事。
- 禁止提交无法编译 / 无法运行的中间状态到 `main`。

### 5.3 提交与评审

- 提交前自查：无调试代码、无敏感信息、无临时文件。
- 敏感信息（API Key、令牌、个人数据）一律不得入库。
- 合并到 `main` 前需通过本地检查（具体检查项待工具链确认）。

> 待确认：是否强制代码评审、是否启用提交钩子校验、版本号规则（SemVer 是否需要）。

## 6. 终端与换行符

- 统一使用 LF 换行，仓库通过 `.gitattributes` 兜底（文件尚未创建，待确认是否需要）。
- 文件名区分大小写视为敏感场景，跨平台协作时避免仅大小写不同的文件。
